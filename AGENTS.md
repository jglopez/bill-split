Notes for AI assistants working on this codebase. Read the code, git history, and repo config for anything not covered here.

## Non-obvious design decisions

**`price` and amount fields are strings in state.** Numeric inputs fight React controlled components on every keystroke. String → float conversion for the authoritative per-person breakdown happens in `calculate.ts`. Components parse prices locally only for display hints (e.g. showing per-checkbox share amounts).

**`assignedTo` stores participant IDs, not names.** Names change; IDs don't. Renaming a participant must not break existing item assignments. `null` = all participants (sentinel that avoids updating every item when participants are added or removed); `[]` = no one assigned; `[ids]` = explicit subset.

**The last item row is always blank.** `useBillSplit` appends a blank row whenever state changes make the last row non-blank. This is the auto-grow mechanism — no "Add item" button needed.

**Tax/tip fields use `inputMode="text"`** to allow the `%` suffix. Item price and payer amount fields use `inputMode="decimal"` because they only ever hold numbers.

**`ParticipantSection` is intentionally isolated.** The participant data source is expected to change (freeform text today, user profiles after OIDC is added). Keep participant management inside that component boundary.

**Settlement uses greedy debt simplification.** See `calculateSettlement` in `calculate.ts` for the algorithm. It minimizes transaction count but doesn't guarantee a unique solution.

**The app reloads itself when a new build is deployed.** Installed web apps (iOS "Add to Home Screen") have no refresh control and can serve a cached page indefinitely. The build emits `version.json` (see `vite-plugins/version.ts`, which also supplies the build ID and version baked into the bundle); `useAutoUpdate` fetches it uncached on launch and on returning to the foreground, and reloads if the build ID differs. It reloads without asking because bill state is persisted on every change. Two guards: it stays off while saving is failing (a reload would lose in-memory state), and it records the target build in `sessionStorage` so a stale cache can't cause a reload loop. Updates are detected by commit SHA, not release tag, because the tag is created in parallel with the deploy and may not exist at build time; the tag is display-only.

**Previews say so in the footer; production doesn't.** `version.json` has `env` (`production` or `preview`). A preview build also records its `branch` and `pr` (the open pull request from that branch, looked up by `scripts/build-release.sh`, or a search for the branch's PRs when that lookup fails), and the footer shows a Preview badge with the branch linking to the PR. Production builds leave `branch` and `pr` out, and the footer stays version and build only. A build is a preview only when Workers Builds builds a branch other than `PRODUCTION_BRANCH` (default `main`); local, Docker and self-hosted builds count as production.

**Bill schema changes go through versioned, lazy-loaded migrations.** `src/lib/migrations/index.ts` owns `CURRENT_BILL_VERSION` and a registry of steps, one file per step (`vN.ts` turns vN into vN+1). Steps are dynamic imports, so their code is fetched only when old data is actually found; current data imports none of it. Saved bills are upgraded in `main.tsx` before the first render, because `useBillSplit` saves on mount and would otherwise overwrite the old bill with defaults. For the same reason, if a step's code can't be fetched, the app shows a reload prompt instead of rendering. `OLDEST_BILL_VERSION` is the oldest version the app still reads; older data is treated as unknown (a saved bill under an older key is ignored, and the app opens blank). The owner retired every step older than it on purpose, because nobody else had used the app yet. Keep writing a step for every schema change from here on. Raising `OLDEST_BILL_VERSION` retires steps and drops support for data people may still have, so only do it when the owner asks. Changing the `BillState` shape means following the checklist at the top of `index.ts`. `meta.test.ts` and `shape.test.ts` fail until the step, its tests, its registration, and a pinned fixture are all in place. Never edit existing fixtures; they stand for bills already saved (and, later, links already shared).

**Every share method goes through one path.** Getting a bill out of the app (summary text, links, exports, payment requests; see #4) uses `shareText` in `src/share/shareText.ts`, which opens the OS share sheet where there is one and copies to the clipboard otherwise (or `copyText` in the same file, for a method that always copies so rich text reaches the clipboard), and a `ShareButton` inside `ShareSection` in the UI. A new share method adds a `ShareButton`; it doesn't build its own share or copy code. `shareText` must run synchronously from the click, because iOS only opens the share sheet during the tap, so a method prepares its content (and loads any code it needs) before the click and keeps its button disabled until then. Share data comes from one format-neutral builder, `buildShareData` in `src/share/shareData.ts`, that every method reuses; don't write a second one.

**The plain-text summary is a LiquidJS template.** `src/share/summary/default.liquid` holds the wording; templates only format, never compute amounts. They see `SummaryTemplateData` (`templateData.ts`), a deliberate, documented subset of the share data that only ever gains fields, so templates written today (and maybe user-written ones later) keep working. LiquidJS was picked because its templates can't run code; `renderSummary.ts` also blocks includes, fails on unknown variables or filters, and caps render time. The engine is a lazy-loaded chunk, so the buttons in `ShareBillButtons` stay disabled until it arrives. "Copy summary" always copies rather than sharing, because the share sheet only carries plain text and the clipboard can also carry the styled (bold and italic) version.

**Bill links never break.** `src/share/link/billLink.ts` is the only code that turns a bill into a link or a link back into a bill; anything else that produces "open in app" links (such as the MCP tools in #146) calls it. The bill is packed into a compact array (`formats/vN.ts`), raw-deflated with `fflate`, and base64url-encoded into the fragment (`#b=<format>.<data>`), which browsers don't send to the server. Each format is tied to the bill schema version it was written for, so old links reuse the bill migrations. A released format never changes: changing the layout or the `BillState` shape means adding a new format and making it the latest, and `billLink.test.ts` fails until the latest format matches `CURRENT_BILL_VERSION` and every format has a pinned link in `fixtures/`. Never edit a pinned link. The encoder is synchronous so a share button can build the link during the tap, which is why it uses `fflate` rather than the async `CompressionStream`. It loads lazily with the summary template engine. Opening a link (`useIncomingLink`) never silently replaces a bill in progress: a blank bill is replaced straight away, otherwise the app asks. The link is then removed from the address bar with `history.replaceState`; the browser's own history list still keeps the visited URL, which no page can change.

**Icons are .svg files, imported as components.** Each icon lives in `src/components/icons/` and is imported with the `?react` suffix (`vite-plugin-svgr`), which turns it into an inline `<svg>` component at build time. Inline SVG keeps `currentColor` working, so an icon follows its parent's text color (hover states, white checks on filled checkboxes); an `<img>` pointing at the file can't. Icon files paint with `currentColor` and carry no size; callers pass `className` and `aria-hidden`. Add a new icon as a file here rather than writing `<svg>` in a component.

**Tests fail on unexpected console output.** `src/test/setup.ts` fails any test that writes to `console.error` or `console.warn`, because React reports misuse (hook dependencies, keys, `act()`) only there and a passing test would otherwise hide it. A test that expects a message mocks the method with `vi.spyOn(console, 'error').mockImplementation(...)` and restores it afterwards. Don't loosen the guard to make a warning go away; fix its cause.

**Deploys run on Cloudflare Workers Builds, not GitHub Actions.** Pushes to `main` deploy production with `npm run build:release`; other branches get a preview URL that Cloudflare posts as a PR comment. Workers Builds sees every push, including ones made with `GITHUB_TOKEN`, so bot workflows never need to dispatch a deploy (they still dispatch auto-release, which a `GITHUB_TOKEN` push doesn't trigger).

**Working from a Claude Code cloud session.** Never deploy from a session: there are no Cloudflare credentials in it, and pushing the branch is the deploy. To check a change in the real runtime, run `npm run preview:worker` (wrangler dev on a local workerd, no login needed) and drive it with the preinstalled Playwright. Read Workers Builds status and logs through the Cloudflare MCP connector. A PR's preview URL arrives in Cloudflare's PR comment. It's on workers.dev, which the cloud environment's network may not allow; if a session can't reach it, check the change with `preview:worker` instead.

## Things to avoid

- Don't add comments that include specific config values — they drift. Describe intent instead.
- The `base` path in `vite.config.ts` defaults to `/` and is overridable via the `BASE_PATH` env var for subpath hosting. Don't hardcode a different default.
- Don't name the production hostname, the owner's other domains, or the owner's private repositories anywhere in this repo: code, docs, issues, PR descriptions, PR comments, commit messages or release notes. Say "outside this repo" instead. Previews use workers.dev, so the hostname never needs to appear.
- Don't add `routes`, `account_id`, or a custom domain to `wrangler.jsonc`. It stays deployable unchanged to any account; the production hostname is attached outside this repo. The MCP server (#146) belongs in this same Worker: add `main` and `assets.run_worker_first` for its path.
